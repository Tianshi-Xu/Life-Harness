- 两者初始均未注入发布版 Life/Meta 策略；AHE 不强制使用 Life 的 H2～H5 分层，但有 NexAU 组件接口和受限能力边界。
- 外部优化模型为 `deepseek-v4-flash`，求解器为本地 `qwen3-4b`。此处 token 仅统计外部优化 LLM 的输入加输出，不含本地求解器 token，不含测试评估，也不是人民币费用。缓存 token 已包含在输入 token 中，不重复相加。

- 两者训练批次、轮次换批策略和优化流程不同，不能把本表当作同题配对实验或同一题集的连续提升曲线。六轮相同不代表 token 预算相同；本记录是迭代次数预算下的实耗／估算对比，不是等 token 预算实验。

## 2. AHE token 估算方法

按用户确认的“缺失调用平均 50,000 token”方案留档。**只估算缺失部分，保留已有 Evolve token 实录**：

- 已记录 Evolve token：207,700,521；对应 2,005 条 tracer generation。
- 当前批次旧 broker 记录 API attempts：3,931。
- 将计数差值视作估算用的缺失调用数：3,931 − 2,005 = 1,926。
- 缺失部分总估算：1,926 × 50,000 = 96,300,000 token。
- 无法从历史日志恢复缺失调用的逐场景、逐轮归属，因此均摊到 3 个场景 × 6 轮 = 18 个单元；每个单元假设 107 次缺失调用。
- 每个场景每轮的缺失补充估算为 107 × 50,000 = **5,350,000 token**。

```text
AHE 当轮估算 token = 当轮已记录 Evolve token + 5,350,000
AHE 累计估算 token = 本场景第 1 轮至当前轮的当轮估算 token 之和
```

重要限制：这是一套约定的估算情景，不是恢复出来的真实逐轮 usage，也不是统计置信区间。API attempts 与 tracer generations 在失败／重试等情况下未必一一对应；差值不能认定全部来自 Debugger。均摊并不表示真实每轮缺失调用恰为 107 次。WebShop 第一轮复用的更早 Debugger 工作不在当前 broker 计数中；修复前归档的启动／演化成本也未纳入。因而下表不是 AHE 历史全链路开销的完整实测账本。
